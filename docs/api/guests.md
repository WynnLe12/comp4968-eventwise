# Guest API contract (Feature 7) — DRAFT

The backend and frontend both build against this document. It is a draft until
Group C approves it; items still open are listed in [section 6](#6-open-decisions).
After approval, message the other side before changing it, then update this file in a pull request.

Guest data lives in the DynamoDB table `EventWise_Guests`
(design: [database/dynamodb/guests.md](../../database/dynamodb/guests.md)).

## 1. Routes

Every route requires a signed-in organizer and checks that the user is a member
of `{eventId}` (`event_members`, either role) before doing anything else.

- Send `Authorization: Bearer <Cognito access token>`, the same header as the other APIs.
- Responses are plain JSON with no `{ "data": ... }` wrapper, like the Vendors and Events APIs.
- `eventId` and `guestId` are strings, as with `event_id` in the Events API.
- The routes use the shared route shape (`backend/shared/http/routes.ts`) and membership check
  (`backend/shared/auth/requireMember.ts`), like the Vendors routes.

| Method | Path | Request body | Success |
| --- | --- | --- | --- |
| GET | `/events/{eventId}/guests` | none | `200`, [GuestList](#3-guestlist-json) |
| GET | `/events/{eventId}/guests/{guestId}` | none | `200`, one [Guest](#2-guest-json) |
| POST | `/events/{eventId}/guests` | [editable fields](#editable-fields) (`firstName` required) | `201`, the created Guest |
| PATCH | `/events/{eventId}/guests/{guestId}` | only the fields that change | `200`, the updated Guest |
| DELETE | `/events/{eventId}/guests/{guestId}` | none | `204`, no body |

- Request and response bodies are JSON (`Content-Type: application/json`).
- The list has no query parameters. Search, group filter and sorting are done in the
  browser from the full list.
- RSVP is not editable in the MVP. `rsvpStatus` is always `PENDING` until Feature 8.

## 2. Guest JSON

```json
{
  "eventId": "42",
  "guestId": "7f3c9a2e-1b4d-4e8a-9c21-5d6f8a0b3e17",
  "firstName": "Sofia",
  "lastName": "Martinez",
  "email": "sofia@example.com",
  "group": "College friends",
  "plusOneAllowed": true,
  "mealChoice": "Vegetarian",
  "dietaryNotes": "No nuts",
  "rsvpStatus": "PENDING",
  "createdAt": "2026-11-12T18:30:00.000Z",
  "updatedAt": "2026-11-12T18:30:00.000Z"
}
```

Optional fields that are empty are returned as `null`, never left out.

### Field reference

| Field | Type | Editable | Rules |
| --- | --- | --- | --- |
| `eventId` | string | no | From the URL; ignored in a request body |
| `guestId` | string | no | UUID generated by the server |
| `firstName` | string | **yes, required** | 1–100 characters after trimming |
| `lastName` | string \| null | yes | Up to 100 characters |
| `email` | string \| null | yes | Valid email, up to 254 characters |
| `group` | string \| null | yes | Up to 100 characters, free text |
| `plusOneAllowed` | boolean | yes | Defaults to `false` on create |
| `mealChoice` | string \| null | yes | Up to 50 characters |
| `dietaryNotes` | string \| null | yes | Up to 500 characters |
| `rsvpStatus` | `"PENDING"` \| `"ATTENDING"` \| `"DECLINED"` | no | Always `"PENDING"` in the MVP |
| `createdAt`, `updatedAt` | string | no | ISO 8601 UTC |

### Editable fields

`firstName`, `lastName`, `email`, `group`, `plusOneAllowed`, `mealChoice`, `dietaryNotes`.
Any other field in a request body is ignored. In PATCH, sending `null` (or `""`) for an
optional field clears it; `firstName` and `plusOneAllowed` cannot be cleared.

## 3. GuestList JSON

`GET /events/{eventId}/guests` returns the guests (oldest first) and the planned headcount:

```json
{
  "guests": [ /* Guest objects */ ],
  "headcount": {
    "invited": 120,
    "plusOnes": 18,
    "expectedTotal": 138
  }
}
```

| Field | Meaning |
| --- | --- |
| `invited` | Number of guests on the list |
| `plusOnes` | Guests allowed to bring a plus-one |
| `expectedTotal` | `invited + plusOnes` |

The headcount is the **planned** headcount. It does not depend on RSVP answers, as required
by Feature 7. RSVP counts (attending/declined/awaiting) come with Feature 8.

## 4. Errors

Errors use the shared `ApiError` format, the same as the Vendors and Expenses routes under
`/events/{eventId}/...`:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Check the submitted fields.", "fields": { "firstName": "Required." } } }
```

`fields` appears only on `422`. Its keys are the JSON field names, so the frontend can show
each message under its input.

| Status | `code` | When |
| --- | --- | --- |
| 400 | `BAD_REQUEST` | Malformed JSON |
| 401 | `UNAUTHENTICATED` | Missing, invalid or expired token |
| 403 | `FORBIDDEN` | The user is not a member of the event. Also returned when the event does not exist or `eventId` is not a valid ID, so the API never reveals which events exist |
| 404 | `NOT_FOUND` | The guest does not exist in this event (including a guest of another event) |
| 413 | `PAYLOAD_TOO_LARGE` | Request body over 16 KiB |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Body sent without `Content-Type: application/json` |
| 422 | `VALIDATION_ERROR` | A field breaks the rules in section 2, or a PATCH body has no editable field |
| 500 | `INTERNAL_ERROR` | Anything unexpected (generic message; details are only logged) |

## 5. Examples

Create:

```http
POST /events/42/guests
Content-Type: application/json

{ "firstName": "Sofia", "lastName": "Martinez", "group": "College friends", "plusOneAllowed": true }
```

→ `201` with the Guest JSON.

Update one field and clear another:

```http
PATCH /events/42/guests/7f3c9a2e-1b4d-4e8a-9c21-5d6f8a0b3e17
Content-Type: application/json

{ "mealChoice": "Vegetarian", "dietaryNotes": null }
```

→ `200` with the updated Guest JSON.
