# DynamoDB table: `EventWise_Guests` (Feature 7)

Stores the guest list of each event. Event data, members and budgets stay in RDS MySQL;
only guests (and later RSVP data) live here.

## Table settings

| Setting | Value |
| --- | --- |
| Table name | `EventWise_Guests` |
| Region | `us-west-2` |
| Partition key | `eventId` (String) |
| Sort key | `guestId` (String) |
| Capacity mode | On-demand |
| Secondary indexes | None for the MVP |

- `eventId` is `events.event_id` from RDS, stored as text (`"42"`). Path parameters are
  always strings, and BIGINT values are kept as strings in the backend, so no conversion
  is needed.
- `guestId` is a UUID generated by the backend (`crypto.randomUUID()`).
- The application reads the table name from the `GUESTS_TABLE_NAME` environment variable
  (default `EventWise_Guests`).

## Item attributes

DynamoDB only enforces the two key attributes. The backend writes the following
attributes; optional attributes are left out of the item when empty (never stored as null).

| Attribute | Type | Required | Notes |
| --- | --- | --- | --- |
| `eventId` | S | yes | Partition key |
| `guestId` | S | yes | Sort key |
| `firstName` | S | yes | |
| `lastName` | S | no | |
| `email` | S | no | Not used in the MVP; needed for invitations (Feature 8) |
| `group` | S | no | Free text, e.g. "Family", "College friends" |
| `plusOneAllowed` | BOOL | yes | Defaults to `false` |
| `mealChoice` | S | no | |
| `dietaryNotes` | S | no | Free text, e.g. allergies |
| `rsvpStatus` | S | yes | `PENDING` / `ATTENDING` / `DECLINED`. Always `PENDING` in the MVP |
| `createdBy` | S | yes | Cognito `sub` of the organizer who added the guest. Not returned by the API |
| `createdAt` | S | yes | ISO 8601 UTC |
| `updatedAt` | S | yes | ISO 8601 UTC |

Example item:

```json
{
  "eventId": "42",
  "guestId": "7f3c9a2e-1b4d-4e8a-9c21-5d6f8a0b3e17",
  "firstName": "Sofia",
  "lastName": "Martinez",
  "group": "College friends",
  "plusOneAllowed": true,
  "mealChoice": "Vegetarian",
  "dietaryNotes": "No nuts",
  "rsvpStatus": "PENDING",
  "createdBy": "a1b2c3d4-0000-0000-0000-000000000000",
  "createdAt": "2026-11-12T18:30:00.000Z",
  "updatedAt": "2026-11-12T18:30:00.000Z"
}
```

## Access patterns

| Operation | DynamoDB call |
| --- | --- |
| List an event's guests | `Query` on `eventId` (paginated) |
| Get / update / delete one guest | `GetItem` / `UpdateItem` / `DeleteItem` on `eventId` + `guestId` |
| Headcount | Computed from the list (see `backend/guest-service/services/headcount.ts`) |
| Filter by group | Done on the list (a few hundred guests per event; no index needed) |
| Delete an event's guests | `Query` on `eventId`, then `BatchWriteItem` in chunks of 25 |

Every call includes `eventId`, so one event's guests can never be read through another
event. Update and delete use `attribute_exists(guestId)` conditions, so a request for a
guest that is not in the event changes nothing and returns "not found".

## Event deletion

DynamoDB has no foreign keys or `ON DELETE CASCADE`. When an event is deleted in RDS,
its guests must be removed by calling `GuestRepository.deleteAllForEvent(eventId)`.
Whoever implements event deletion needs to call it.

## Post-MVP (not created yet)

- `rsvpToken` attribute plus a global secondary index `rsvpToken-index`, so a guest's
  private RSVP link can find the guest without knowing the `eventId` (Feature 8).
- `plusOneName`, `rsvpRespondedAt`.

New attributes need no migration; the index can be added to the existing table.

## Local development

The repository's `GuestRepository` connects to DynamoDB Local when `DYNAMODB_ENDPOINT`
is set (for example `http://127.0.0.1:8000`) and uses the same table definition.
